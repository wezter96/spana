Spana is a TypeScript E2E framework where one test runs on Web, iOS, Android, Electron, and
Electrobun. No single framework wins every row — this page grades **9 E2E frameworks** honestly on
platforms, authoring, CI scale, debugging, AI workflows, ecosystem maturity, and speed so you can
pick the right tool for your stack (even when that tool isn't Spana).

:::note[Direct CDP + Playwright compatibility]
On Chromium, Spana's `engine: "auto"` / `"cdp"` talks directly to Chromium over a raw CDP
WebSocket (bypassing Playwright's Node client↔server pipe, including cross-origin OOPIF iframes,
live screencast video playback, and pre-warmed isolated `BrowserContext` pools). When you choose
Firefox, WebKit, or Playwright-specific options like HAR recording, Spana seamlessly uses its
bundled Playwright driver with the exact same flow API.
:::

:::tip[How Speed Scores are calculated (be skeptical!)]
Only **Spana** and **Playwright** web numbers are directly measured in our local benchmark below.
Speed scores for the other 7 frameworks reflect real-world protocol overhead, context/app isolation
cost, and local parallelism on each framework's **primary** platforms (so Detox scores **8.5 / 10**
for gray-box React Native speed even though it doesn't run on web, and Playwright scores **8.5 / 10**
as the gold-standard multi-browser web runner). **8.0–10** = Green, **5.5–7.9** = Yellow, **&lt; 5.5** = Red.
:::

## Benchmarks

Web runs: Apple M4 Pro, Bun 1.4.5, headless Chrome. 20 flows with 14 steps each (280 steps in
total). Playwright and Spana sign in once through the UI, then reuse the session for the other
flows.

How the other tools are run:

- **Playwright** rows use the Playwright library directly (one browser, a new context per flow).
  They do not use the `playwright test` runner.
- **WebDriver HTTP** is a simulation of the W3C WebDriver protocol that WebdriverIO uses: plain HTTP
  calls to a small local WebDriver server. It does not use the `webdriverio` package, so treat it
  as a rough guide to protocol cost, not a WebdriverIO result.

### 1. Strict apples-to-apples (fresh context per flow, full actionability, no bridge)

Both Playwright and Spana open a brand-new isolated browser context per flow, execute all 20 flows
(280 interactions) with full actionability checks (visibility, enabled, scroll-into-view, hit-test
unobstructed, stability) and no app-side bridge script:

| Setup                                            | Mode / Isolation           |  Total time | Compared with               |
| ------------------------------------------------ | -------------------------- | ----------: | --------------------------- |
| Playwright, `storageState`, 1 worker             | 1w, fresh context/flow     |     17.71 s | baseline (PW 1w)            |
| **Spana Direct CDP (`engine: "cdp"`), 1 worker** | 1w, fresh context/flow     | **11.34 s** | **1.56× faster than PW 1w** |
| Playwright, 4 parallel workers                   | 4w, fresh context/flow     |     15.57 s | baseline (PW 4w)            |
| **Spana Direct CDP Pool, 4 workers**             | 4w, fresh context/flow     |  **9.34 s** | **1.67× faster than PW 4w** |
| **Spana Direct CDP + Video Playback, 4 workers** | 4w, fresh ctx + screencast |  **9.73 s** | **1.60× faster than PW 4w** |

### 2. Optional speed tiers (different isolation trade-offs)

These modes trade creating a brand-new context per flow for faster state resets or an optional
in-app bridge script. They are listed separately so you can choose the right trade-off for your suite:

| Setup                                       | Trade-off vs fresh context                    | Total time | Reference vs PW 4w |
| ------------------------------------------- | --------------------------------------------- | ---------: | ------------------ |
| **Spana Direct CDP `hot-cache`, 1 worker**  | Keeps HTTP & V8 cache warm; wipes all state   | **6.01 s** | 3.0× vs PW 1w      |

- **1920×1080 PNG visual regression diff:** Pure-JS `pixelmatch` `215.0 ms` → **Spana Rust FFI `11.2 ms`** (**19.2× faster**).

### Mobile (iOS / Android)

Mobile timings depend heavily on local Xcode Simulator / Android Emulator hardware and are **not**
measured by `benchmarks/framework-comparison/benchmark.ts` (we removed earlier unmeasured constant
estimates so every benchmark table only reports live-measured numbers). Spana avoids Appium server
hops by talking directly to WebDriverAgent (iOS) and UiAutomator2 (Android) and resolving WebView
elements over CDP / WebKit Inspector / `spana-bridge`.

### Pull requests (subset filtering)

With `--changed-since origin/main` and `pathRuleFilter`, Spana ran only the **5 of 20** flows a PR
change could affect, in `2.76 s` (4w Direct CDP). This is **not** a full-suite speed comparison — it
measures the wall time saved by skipping unaffected flows in CI.

## When to pick something else

- **Playwright** — your app is web-only and you want the largest community, the best time-travel
  Trace Viewer (`trace.zip`), first-class VS Code debugging, or Python / Java / .NET SDKs.
- **Cypress** — you want mature built-in Component Testing (React, Vue, Angular, Svelte) and an
  interactive in-browser time-travel runner for frontend teams.
- **WebdriverIO** — you want a battle-tested OpenJS ecosystem with real Safari, official Electron &
  component runners, or an existing WebDriver / Appium grid.
- **Maestro** — you want ultra-simple YAML mobile tests that non-developers and QA teams can read
  and write with minimal boilerplate.
- **Detox** — you test only a React Native app and want gray-box synchronization directly with the
  app's JavaScript thread and timers.
- **Appium** — you need native desktop/TV drivers Spana does not have (macOS, Windows, tvOS, Roku),
  every real-device cloud out of the box, or Java / Python / C# / Ruby tests.
- **Argent** — you're a React Native / TV / macOS team that wants deep Hermes, React DevTools,
  Xcode Instruments, and Perfetto profiling driven directly by AI coding agents.
- **`e2e`** — you want natural-language `agent.act()` / `agent.assert()` steps mixed directly into
  TypeScript tests with built-in CLI replay caching.

## When Spana fits best

- One app across **Web, iOS, Android, Electron, and/or Electrobun** maintained in a single typed
  TypeScript (or Gherkin) suite.
- A **Capacitor, Ionic, React Native, or Electron** app with `testID` attributes where dual-channel
  DOM + native access avoids Appium setup.
- You want **Chromium Direct CDP speed** (1.5–1.7× strict, up to 3.8× `hot-cache`), Rust visual
  diffing, and PR diff filtering with zero paid CI gates.
- You want a **model-free MCP server** (`spana mcp`) so coding agents can inspect screens, drive
  live sessions across all 5 targets, and export deterministic `.flow.ts` tests.
